## What already exists (and why EasyDataTransfer still wins)

P2P web transfer tools exist — tools like the P2P File Transfer app use WebSocket for handshaking and WebRTC for the actual transfer, with a 6-digit token exchanged between peers. ToffeeShare does direct device-to-device transfer with end-to-end encryption and no cloud storage. Academic tools like Peer Copy use libp2p and IPFS DHT for peer discovery with password-authenticated key exchange.

**None of them have:** biometric gating on both ends, a floating persistent widget (like a live sports score), or a session that auto-expires with a hard TTL. That's your moat.

---

## The full blueprint

### Core idea: two-sided biometric handshake over a zero-storage relay

The server never sees your files. It only brokers the introduction between two authenticated peers, then gets out of the way. The data flows directly device-to-device over an encrypted WebRTC DataChannel.

### The floating widget

This uses the **Web Push API + Service Worker + Picture-in-Picture / document-pip** pattern. When the user taps "Wake up transfer", a Service Worker registers and a small persistent overlay appears — similar to how Google surfaces live sports scores as a floating card. On Android/iOS PWA, this becomes a lockscreen/home notification widget. It signals "this session is live" without keeping a browser tab open.

### Auth flow

WebAuthn is the W3C standard for this. It supports fingerprint, face scan, and PIN — and critically, biometric data never leaves the device or travels over the network. The browser verifies locally and sends a signed cryptographic assertion to your server instead. Your server stores only the user's public key — never the biometric itself — and verifies signed assertions on each auth attempt.

**Sender side:** WebAuthn challenge → device signs with private key → server issues a short-lived HMAC session token (1-hour TTL). That token is what gets "advertised" to the signaling layer.

**Receiver side:** Same WebAuthn flow → server checks their signature → matches it against an advertised sender token → if matched, releases the WebRTC answer so the direct channel opens.

### The session token / matching mechanism

This is the clever part. The sender's token is a signed payload containing:
- A random session ID
- The sender's WebAuthn public key fingerprint  
- Expiry timestamp (now + 1hr)
- Permitted asset type (optional: image-only, any, etc.)

The receiver doesn't need to "know" the sender's token in advance. They just authenticate on their device, and the signaling server matches them automatically if there's an unmatched advertised session with a valid token. This is the "auto-discovery" feel you described — you don't share a code, you just both authenticate and the server pairs you.

### What the server does vs doesn't do

| Does | Doesn't |
|---|---|
| WebSocket signaling (SDP offer/answer) | Store any file or asset |
| HMAC token validation | See plaintext biometric data |
| STUN/TURN NAT traversal | Log payload content |
| TTL enforcement (Redis) | Persist sessions after 1hr |

### Stack recommendation

**Frontend:** Next.js PWA — gives you Service Workers, Web Push, and installability out of the box. WebAuthn via the browser's native `navigator.credentials` API.

**Signaling backend:** Node.js with `ws` (raw WebSocket library) — lightweight, stateless. Redis for session token storage with TTL auto-expiry.

**STUN/TURN:** Self-hosted `coturn` on a cheap VPS, or use Metered.ca's free TURN tier initially. TURN is only needed when both peers are behind symmetric NATs (~15% of cases) — the rest goes fully P2P.

**Infra:** Vercel/Netlify for the frontend (global CDN), Fly.io or Render for the signaling server (low-latency WebSocket), Cloudflare in front of everything for DDoS protection.

**Encryption on the wire:** WebRTC DataChannel is already DTLS-encrypted. Layer AES-256-GCM on top using the Web Crypto API for end-to-end guarantees — so even if someone intercepted the TURN relay, the payload is unreadable.
